# Contributing

Thanks for looking at Kubemoot. This file is the org default; a repo can add its own
`CONTRIBUTING.md` for anything specific to that codebase.

## Getting started

1. Fork the repo you want to change and clone your fork.
2. Create a branch off `main`: `git checkout -b your-topic`.
3. Make your change.
4. For the `kubemoot` repo specifically, run the quickstart against a local `kind`
   cluster as your smoke test before opening a pull request:

   ```bash
   kind create cluster --name kubemoot
   ./quickstart/quickstart.sh
   ```

   It installs the operator, a small CPU model, and a two-agent crew, then asks the
   crew a question and checks that an answer comes back. If it breaks, your change
   broke something a real user would hit first.
5. Open a pull request against `main` using the PR template.

## Commit messages: Conventional Commits

Versions come from git tags, generated by CI from your commit messages. Never type a
version number by hand. Use a [Conventional Commits](https://www.conventionalcommits.org/)
prefix:

| Prefix | Bump |
|---|---|
| `fix:` | patch |
| `feat:` | minor |
| `docs:`, `chore:`, `refactor:` | patch |
| `feat!:`, `fix!:`, or a footer containing `BREAKING CHANGE` | major |

## Tests ship with the code they cover

No pull request adds a function, method, or class without a test for it, covering
both the expected input and at least one unexpected one. Tests are not a follow-up
task.

## Code quality

No function should exceed a cyclomatic complexity of 10. If you find yourself past
that, extract methods, use a dispatch table, or decompose the conditional before
opening the pull request. Repos with a linter configured (Go, Java, TypeScript, Rust)
run it in CI; a red check on this means refactor, not override.

## Built with AI assistance

This project is built with AI coding assistance. Contributions from AI assistants are
welcome and are held to the exact same gates as anything else: tests, complexity
limits, and review. The code is judged on what it does, not on who or what typed it.

## Response time

Kubemoot has a single maintainer. Response to issues and pull requests is best
effort, not guaranteed within any particular window. If your pull request sits
without a review, a polite ping after a week or two is fine.

## Questions vs. defects

- **Have a question, or not sure if something is a bug?** Open a
  [Discussion](https://github.com/orgs/kubemoot/discussions) instead of an issue.
- **Found a defect?** Open an issue using the bug report template. If it is the
  quickstart itself that failed, use the quickstart-failed template; it asks for the
  exact information needed to reproduce a fresh-cluster failure.
